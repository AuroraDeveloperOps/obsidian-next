# Obsidian CLI Research & Architecture Analysis

**Status**: Final
**Author**: Aurora Labs
**Date**: 2026-01-29

## 1. Executive Summary
This document synthesizes extensive research into the current state of AI Command Line Interfaces (CLIs), including analysis of GitHub Copilot CLI, Claude Code, and open-source alternatives (Aider, Roo). It defines the architectural blueprint for "Obsidian," a robust, open-source, "Bring Your Own Key" (BYOK) agent system.

## 2. Competitive Analysis & Feature Sets

### 2.1. GitHub Copilot CLI
- **Core Value**: Translating natural language to shell commands (`??` syntax).
- **Strengths**: Deep integration with GitHub ecosystem (PRs, Issues).
- **Weaknesses**: Historically rigid "request-response" loop; less autonomous than newer agents.
- **Obsidian Takeaway**: Must support a "Plan Mode" that allows users to review complex actions (`fs` writes) before execution.

### 2.2. Claude Code (Anthropic)
- **Core Value**: "Pair Programmer" that lives in the terminal.
- **Strengths**:
    - **Context Management**: Smartly compacts conversation history to save tokens.
    - **Rich UI**: Markdown streaming, "Thinking" spinners, and interactive permission requests.
    - **Slash Commands**: `/init`, `/cost`, `/clear` provide clear control surfaces.
- **Obsidian Takeaway**: We will adopt the **Ink** framework (React for CLI) to match this high-fidelity UX. We will implement "Slash Commands" for meta-control.

### 2.3. Open Source Landscape (Aider, Roo Code)
- **Aider**: Focuses on Git-centric workflows (auto-committing). Uses a "Repo Map" to optimize context.
- **Roo Code**: Integrates browser testing (Puppeteer) for web apps.
- **Obsidian Takeaway**: Git integration is a baseline requirement. We will treat the "Repository" as the primary unit of context.

## 3. Architecture & Tech Stack

### 3.1. Core Stack
| Component | Technology | Rationale |
|-----------|------------|-----------|
| **Runtime** | Node.js (TypeScript) | Extensive ecosystem, `ink` support, MCP SDK availability. |
| **CLI UI** | **Ink** (React) | Best-in-class for complex, interactive terminal UIs (markdown, spinners). |
| **Database** | **Postgres** + `pgvector` | Standard relational data + Semantic code search in one reliable engine. |
| **Cache** | **Redis** | High-performance cache for "Hot" context and Pub/Sub for agent events. |
| **Security** | `isolated-vm` | Industry-standard V8 isolation for executing untrusted planning scripts. |

### 3.2. Agentic Pattern: "The Supervisor Loop"
We will move beyond simple "Chain of Thought" to a **Supervisor-Worker** delegation pattern.

1.  **Orchestrator (Supervisor)**:
    - Receives user input (Main Thread).
    - Analyzes intent ("Write code", "Research", "System Op").
    - Delegates to a specialized sub-agent or MCP tool.
2.  **Specialist Agents (Workers)**:
    - **Planner**: Breaks down requests into `task.md` steps.
    - **Coder**: Edits files (Sandboxed).
    - **Researcher**: Uses `brave-search` (MCP) to find info.
3.  **Message Queue**:
    - Powered by **Redis**. Allows asynchronous inter-agent communication without blocking the main UI thread.
4.  **Event Bus (Structure-First)**:
    - Agents do **NOT** stream raw text. They emit typed events:
      - `{"type": "thought", "content": "..."}`
      - `{"type": "tool_start", "tool": "bash", "args": "ls -la"}`
      - `{"type": "choice", "options": [...]}`
    - This allows the Ink UI to render precise grid layouts (`●`, `⎿`) instead of unstructured streams.

## 4. Security & Safety (The "No Slop" Standard)

### 4.1. Sandboxing
- **Problem**: Agents generating scripts (`rm -rf /`) is dangerous.
- **Solution**: All "planning" or "reasoning" code generated by the model runs inside **`isolated-vm`**.
- **Constraint**: No direct access to `process` or `fs` unless explicitly injected via a Permission capability.

### 4.2. Human-in-the-Loop
- **Default**: ALL file modifications require a "Y/n" confirmation.
- **Auto-mode**: Can be enabled for specific paths (e.g., `/tmp/*` or test directories) but never for root or config.

## 5. Visual Design System ("The Look")

### 5.1. Philosophy
### 5.1. Philosophy
- **Grid Alignment**: Output is strictly aligned to the "Agent Grid" (`●` for thoughts, `⎿` for data).
- **Structure**: No "Wall of Text". Use tables, lists, and choices.
- **Kinetic**: "Morphing" spinners (`⠶` -> `⠘`) that "breathe".

### 5.2. Interaction
- **Shift+Tab**: Cycles through context modes (e.g., `[Chat] -> [Plan] -> [Exec]`).
- **Spinners**: Custom `ink-spinner` frames for different states (Thinking, writing, waiting).

## 6. Integration & Distribution

### 6.1. Model Context Protocol (MCP)
- Obsidian will act as a **Host** for MCP Servers.
- **Local Integration**: First-class support for **Ollama**. Users can route "sensitive" queries to a local Llama 3 instance transparently.

### 6.2. Packaging
- **Binary**: Packaged via `pkg` (Node) to a single executable.
- **Docker**: Optional container for completely isolated runs.

## 7. End-to-End Testing Strategy
To ensure the UI "adheres to these outputs", we need rigorous E2E testing.

### 7.1. Ink Testing Library
- **Unit**: Test individual components (`MorphSpinner`, `ChoiceList`) for rendering correctness.
- **Integration**: Test the `Root` component by emitting mock Events and asserting the text output.
- **Snapshots**: Store accepted output states to prevent regression.

### 7.2. "Ghost" Agent
A mock Agent that emits pre-defined sequences of events to verify the CLI handles them:
1.  Emit `ToolStart` -> Verify `⎿` appears.
2.  Emit `ChoiceRequest` -> Verify List appears.
3.  Simulate Keypress `Down` -> Verify selection change.

## 9. Next-Gen Agentic Patterns (2025/2026)
Based on deep research into "Zero Hallucination" and "Zero Context Loss".

### 9.1. "The Auditor" (Calibrated Uncertainty)
- **Problem**: Agents hallucinate file paths or imports.
- **Solution**: A lightweight "Pre-flight Check" loop.
  - Before emitting a `ToolCall` for `fs.write`, the Agent queries the Shadow Context: "Does `src/utils.ts` actually exist?"
  - If NO, it self-corrects: "I need to `fs.list` first."
- **Implementation**: The `Supervisor` runs a "Sanity Check" on every critical tool call against a simplified `FileMap` in memory.

### 9.2. Context Slicing (Zero Loss Strategy)
- **Problem**: Dumping 20 files into context causes "Middle-lost" phenomenon.
- **Solution**: **Context Slices**.
  - Instead of "All Context", the Supervisor creates named slices:
    - **@Auth**: `src/auth/*`, `db/schema.prisma`
    - **@Routing**: `src/app/*`, `next.config.js`
  - Agents subscribe to a Slice, minimizing noise tokens.

### 9.3. Hybrid MCP Architecture
- **Supervisor**: Acts as the **MCP Host**.
- **Workers**: Act as **MCP Servers**.
- **User**: Connects as a Client.
- The Supervisor aggregates Tool Definitions from all Workers (`Researcher`, `Coder`) and exposes a unified "Capability Map" to the active Planner.
